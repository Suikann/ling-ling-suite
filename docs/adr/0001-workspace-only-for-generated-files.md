# 工作區只收程式產生的檔案，匯入的檔案原地不動

分割輸出原本直接落在合併譜所在的資料夾、只以樂器命名，多首曲目的合併譜放在同一處時必然互相覆蓋，並連帶讓兩個群組引用同一路徑、重新命名中途失敗。我們決定把分割輸出放進程式自己管理的工作區（`APPDATA_DIR/workspace/<來源路徑雜湊前 8 碼>/`），但**使用者匯入的既有 PDF 不進工作區**：這是重新命名工具，使用者預期原檔被搬走改名，複製一份進工作區會留下要手動刪的原檔並使空間翻倍，直接搬進去則會讓使用者在檔案總管突然找不到檔案。

## Considered Options

- 分譜放在合併譜旁的同名子資料夾：隔離效果相同，但中間檔散落在使用者的資料夾裡，沒有固定的地方可以清理。
- 子資料夾以「來源所在資料夾 - 檔名」命名：可讀，但路徑長度綁在使用者無法控制的檔名上，Windows 的 260 字元上限容易超過。改為路徑雜湊後，工作區前綴長度為常數，可讀性由子資料夾內的 `meta.json`（來源路徑、所屬專案）與清理對話框補回。
- 匯入檔案也複製或搬進工作區：見上文，否決。

## Consequences

- `rename_file` 必須處理跨磁碟搬移（工作區在系統碟，輸出常在其他磁碟或同步資料夾）：`os.rename` 失敗時改為複製到 `.part` 再就位，失敗不留半成品。
- 專案檔格式不變，路徑仍是純字串；舊版程式開新版專案照常運作。
- 工作區內未被任何已知專案（最近清單與各子資料夾 `meta.project_path` 指向者）引用的孤兒檔需要「清理工作區」手動處理，清理走資源回收桶；存在別處且未曾記錄的專案檔無法得知，這是接受的誤判範圍。
- 例外：搬空後只剩 `meta.json` 的子資料夾由掃描直接刪除、不走資源回收桶，因為 `meta.json` 是程式自產的中繼資料，不含使用者資料。
- 程式寫出的 JSON（專案檔、`meta.json`、`preferences.json`、復原／重做紀錄、Google 權杖）一律原子寫入：先寫到同資料夾的暫名並 fsync，再以 `os.replace()` 就位，目標被同步客戶端／防毒短暫鎖住時短暫重試；磁碟上只會是完整的舊版或完整的新版，不會出現截斷或空檔。損毀專案檔的剩餘來源（磁碟錯誤、手動編輯）不做修復流程：這些來源發生機率低，且修復只能猜測遺失的內容、無從驗證，損毀的專案檔仍是跳過。
