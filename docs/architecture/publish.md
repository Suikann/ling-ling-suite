# Publish

發譜把群組的編制、分譜與總譜寫進 HuaXia（spec #82）。泠靈以幹部自己的 Discord 帳號直接寫入 HuaXia 的 Supabase，所有請求經 `services/huaxia_client.py` 的 `HuaXiaClient`（[ADR 0003](../adr/0003-lingling-writes-huaxia-directly.md)）；泠靈依賴 HuaXia 的資料表、欄位、發譜函式與 Storage 路徑格式以依賴說明文件為準，複本在 [docs/huaxia/LINGLING.md](../huaxia/LINGLING.md)。按下「發譜」前的檢查與預覽各步的規則在 `services/publish_service.py`（入口見 [modules.md](modules.md)），本文件記預覽按下「發譜」之後的事。

## 開始前

預覽可能開了很久，在預覽按下「發譜」時依序：

1. **新曲目的編號**：要新建曲目、還沒有編號的群組由 `PublishPreview.assign_piece_ids` 產生編號寫進專案，主視窗接著自動存檔一次（只寫專案檔，不寫回譜庫）。按下「發譜」時專案只會有預覽寫進去的改動（曲目的對應與手動挑的聲部配對），一起存下，那正是要記在專案檔的對應。存不成就不發。已經有編號的（上次發到一半）沿用：發譜函式遇到已存在的編號就沿用那首，重發不會重複建曲目。
2. **重查**：`PublishRunner.start` 以 `publish_service.recheck` 重查幹部身分（不是幹部就登出）與發譜函式的版本，缺少或不符時不發，畫面說明要請 HuaXia 維護者處理哪個合併請求。
3. **快照**：都過了才做快照（見下節）。不能發、或快照失敗時，預覽交出、要傳的壓縮檔一併丟掉。

這三步在等待視窗裡做；之後的發譜在背景，不擋主視窗。

## 快照

發出去的是按下「發譜」那一刻的檔與編制，之後在泠靈裡改什麼、原檔被重新命名搬走都不影響這次發譜：

- 要傳的本機檔複製到暫存資料夾（`TEMP_DIR`）底下這次的子資料夾，以複本的內容算 SHA-256 與泠靈的 Storage 路徑；壓縮過的檔本來就在暫存資料夾，直接用。
- 人數、聲部組、要建與要覆寫的聲部、要撤掉登記的舊樂譜、要掛的公演都在這一刻取值成 `GroupSnapshot`，之後不再碰專案。
- 清舊檔要刪的檔扣掉這次自己要用的（例如原檔在預覽之後被改回 HuaXia 上那份舊的內容）。
- 快照與要傳的壓縮檔在發譜結束（成功、失敗、取消）時刪掉；沒刪到的（例如發譜中關閉泠靈、等不到它停下）下次啟動時連同暫存資料夾一起清掉（[data-storage.md](data-storage.md)）。

## 三段式

`PublishRunner.run` 在背景執行緒照快照發譜：

0. **開始發譜**：經譜庫服務寫一列列「開始發譜」到譜庫的發譜紀錄（見下節），寫不進去就什麼都不做，HuaXia 上沒有任何變動。
1. **傳檔**：每首曲目先列出 Storage 裡泠靈資料夾（`lingling/<曲目編號>/`）已有的檔，路徑相同的就是內容相同，跳過；其餘同時傳 3 份（`UPLOAD_WORKERS`），先不登記，團員看不到。Storage 不覆寫，上傳時已有檔也當成傳好了。同一份內容（同一個路徑）只傳一次。
2. **切換**：一個群組呼叫一次 HuaXia 的發譜函式，在一個交易裡完成這個群組的寫入（新建曲目、建聲部、改人數與聲部組、撤掉舊樂譜的登記、登記新樂譜、掛場次），全成或全不成。有檔沒傳上去的群組不呼叫；某個群組失敗不影響其他群組。預覽到執行之間幹部在網頁上刪了聲部時，那個群組切換失敗、列在沒發成的群組裡。
3. **清舊檔**：刪掉被取代的舊檔本體。只刪發譜預覽算出的 `GroupPublish.deletes`（被取代、切換後沒有任何樂譜登記還指著、這次也沒再用到的），而且要撤掉指著它的登記的那些群組**都切換成功**：兩個群組對到同一首、各自撤掉指著同一個檔的登記時，其中一個切換失敗，那個檔它還登記著，不刪。
4. **發譜結果**：補一列列「發譜結果」，寫不進去時 HuaXia 照樣已經變動，主視窗寫明。

每個群組的結果也寫進紀錄檔（`ActivityLog`），不記 HuaXia 傳回的團員資料。

### 取消與中斷

- 第 1 段按下就停：還沒開始傳的不傳，正在傳的傳完，不切換，HuaXia 的資料表沒有變化。
- 第 2 段做完目前這個群組就停，之後的群組列為取消、不清舊檔。
- 第 3 段做完目前這個群組就停，沒刪的舊檔成為孤兒檔。
- 發譜進行中關閉泠靈時問要不要中斷；中斷等同斷線。

重發會從中斷處接著做：已傳的檔在第 1 段列出時跳過，新建曲目的編號沿用，發譜函式重跑不重複建曲目；那首已在 HuaXia 上時預覽以它已有的聲部與樂譜配對，已建好的聲部不再建，已登記、內容相同的檔不重傳也不取代（`PublishFile.unchanged`）。

### 孤兒檔

泠靈路徑格式、但沒有樂譜登記的 Storage 檔：第 1 段傳了、那個群組卻沒切換的新檔，以及第 3 段沒刪成的舊檔。團員看不到它們（只有登記的樂譜才列在網頁上），本次的結果列在 `PublishOutcome.orphans`（舊檔）與各群組的 `GroupOutcome.uploaded`（新檔）。

## 發譜紀錄

譜庫的「發譜紀錄」工作表（`SHEET_PUBLISH_LOG`）只新增、不修改，經譜庫服務的 `begin_publish`、`record_publish` 寫入，每次寫入的請求數固定。每次發譜一個發譜編號，「開始發譜」與「發譜結果」各是每個群組一列，以發譜編號串起來；一列的欄位與 JSON 內容見 `core/publish_log.py` 的 `PublishRecord`：

- 開始發譜：要做的（要新建的曲目與聲部、要覆寫的聲部的原值與新值、要傳與要登記的檔、要撤掉登記的、要刪的、要掛的場次與結束時間）。
- 發譜結果：做到的。新建的聲部、登記與撤掉登記的樂譜帶 HuaXia 的編號（發譜函式的輸出），撤回只動這些；沒發成的群組寫出在哪一段與原因，只留這次傳上去的檔。

只有「開始發譜」、沒有「發譜結果」的發譜編號是中途停下（例如關閉泠靈、等不到它停下）或結果寫不進譜庫的。

## 進行中

照原型 #63 的變體 C，不擋主視窗、不鎖操作（發出去的是快照）：發譜進行中可以照常編輯專案、重新命名與分割，包括正在發譜的群組，之後的改動要再發一次。發譜有自己的背景工作（`MainWindow._publishing`，與其他長工作分開），一次只有一個發譜，進行中「發譜」停用。

- 狀態列顯示總進度（傳檔、切換、清舊檔的步數合計）與「停止發譜」。
- 主視窗下方是這次發譜的逐行紀錄（`ui/publish_run.py` 的 `PublishRunPanel`），完成時接上結果，下方列出沒發成的群組與原因。
- 「開始發譜」或「發譜結果」寫不進譜庫時頂端顯示譜庫的提示列。
- 發譜進行中關閉泠靈時問要不要中斷，並說明重發會從中斷處接著做；中斷就要求取消、等它停下（最多 `CLOSE_WAIT_SECONDS` 秒）再關閉。
