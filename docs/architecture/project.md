# Project

## 專案編輯

專案（`core/models.py` 的 `Project`）自己管理修改、檔案引用與未存檔狀態，是純記憶體的物件（`core/` 的界線見 [CODING_STANDARDS.md](../../CODING_STANDARDS.md)）。

- UI 只表達意圖並立即寫入：修改一律呼叫 `Project` 的公開編輯操作（`update_group`、`add_group`、`move_to_group`、`apply_split`、`guess_piece_name`…，完整清單看 `Project` 的公開方法），不直接指定 `Project`、`Group`、`FileInfo` 的欄位
- 舊欄位鏡像（`selected_instruments`、`use_parts_subfolder`）由編輯操作與載入流程維持，呼叫端不碰
- 群組分頁、編制表、預覽對話框不呼叫主視窗的私有方法：群組分頁以 `groups_changed` 讓主視窗重建分頁（影響其他分頁的修改），編制表改了聲部清單時發出 `instruments_changed`（主視窗據此重新顯示各分頁），預覽對話框用主視窗注入的 callback（`check`、`on_execute`）
- 同一份樂器表不重名：新增（`add_instrument`）或改名（`rename_instrument`）成與其他列同一聲部的名稱（`core/voice_names.py` 的規則，例如已有「二胡 I」時的「二胡1」）時丟出 `DuplicateVoiceError`、樂器表不變，編制表顯示說明並還原名稱；改成自己的另一種寫法不算重名。整份換掉樂器表（`set_instruments`：預設樂器表、從檔名擷取）、移動與移除不檢查，舊專案已有的重名原樣保留
- 編制表顯示目前分頁那個群組的編制；目前分頁不是群組（未分組）時清空並停用，輸入的聲部才不會沒有地方寫入（`InstrumentationTable.show_group`）

### 編制表

主視窗左欄就是編制表（`ui/instrumentation_table.py` 的 `InstrumentationTable`），取代原本的樂器表清單；左欄與右邊之間的分隔線可以拖寬。聲部的增刪與順序只在這張表，每個動作經下一節的編輯操作：

- 欄位：本專案有、聲部、最少、最多、以上、聲部組，聲部組旁寫出會跟著改的其他編號（`same_instrument_voices`）。欄位依 `COLUMNS` 的順序排；表格上方是群組的時長（分、秒）
- 人數三欄（`set_headcount`）與時長（`set_duration`）打完（按 Enter 或離開欄位）才寫入，寫入後只把整理過的值填回那一列，不重畫整張表；勾「以上」時清空並停用最多
- 「從其他群組複製編制」選單列出專案裡的其他群組，選了就 `copy_instrumentation`，表格下方寫出對應不到、人數已留空的聲部
- 只有改了聲部清單（增刪、改名、拖動、本專案有）才發出 `instruments_changed`；人數、時長、複製編制與聲部組不影響配對，不發出（複製編制與聲部組只重畫這張表）
- 舊的「編制設定」對話框（編輯人數）已拿掉，人數只在這張表填
- 拖動列：`move_instruments`，分譜跟著聲部走；分譜在群組分頁單獨拖動（`reorder_files`），只改配對。群組分頁每份分譜寫出它自己配到的聲部，沒有分譜的聲部不列
- 雙擊改聲部名稱：`rename_instrument`；清空名稱等於移除那一列
- 輸入欄與改名的編輯欄有聲部名稱的自動完成（見 [modules.md](modules.md)）：只提示、不改寫輸入，選到的名稱照樣經 `add_instrument`、`rename_instrument` 的不重名檢查
- 勾選「本專案有」：`set_present`；取消勾選、移除列（`remove_instruments`）時，表格下方寫出移到未分組的分譜
- 連到譜庫的群組移除列（含清空名稱）前先確認，寫明這等於從樂譜刪除；快照記著已有 Drive 檔案的聲部（`Project.filed_voices`）不移除，說明要到譜庫視窗處理，改名成別的聲部也一樣（見「寫回譜庫」）
- 連到譜庫的群組，聲部組旁另寫出譜庫裡用到這種樂器的其他曲目數（`CatalogLink.other_pieces_using`，例如「其他 12 首的柳琴也會跟著改」），因為改的是全社團的對照
- 與另一列是同一聲部的列（舊專案留下的重名，`core/voice_names.py` 的 `duplicate_rows`）標紅；重名不自動改名，重新命名與分割照常可用
- 元件不依賴主視窗：帶入專案後以 `show_group` 顯示任何一個群組；在別處改了專案設定（例如樂團類型）後以 `refresh` 重畫。上方的 `header` 版面放群組連到譜庫的哪裡（見下方「連到譜庫」）、未同步的提示列（見下方「未同步」）與聲部清單變了的提示列（見下方「開啟時更新快照」）

### 聲部與分譜的配對

- 群組的樂器表逐列帶「本專案有」（`Group.present`，與 `instruments` 逐列對應，存進專案檔；沒有這一欄的舊檔全都有）。它只存在專案：這場缺某份分譜時取消勾選，不必刪掉聲部
- 每個聲部配自己的分譜，本專案有的聲部也可以沒有分譜。存法：分譜清單（`Group.files`）依序配給接分譜的聲部（`Group.part_voices`：本專案有、沒標沒有分譜的列），第 N 份配第 N 個；本專案有而沒有分譜、後面還有分譜的列標成沒有分譜（`Group.vacant`，逐列對應，存進專案檔），配對時跳過，所以不會接走後面聲部的分譜。沒有這一欄的專案檔（含舊版）每個本專案有的聲部都接分譜，開啟時配對與存檔時相同、不算修改
- `Group.pairing` 列出本專案有的每個聲部與它的分譜（沒有的為 None）；多出的分譜（`Group.extra_files`）沒有聲部、不改名。序號仍是聲部在樂器表中的位置（見 [naming.md](naming.md)）
- 編輯操作讓分譜跟著聲部，沒動到的聲部的分譜不變（重排各列一律經 `core/models.py` 底部的 `_VoiceRow`、`_place_rows`，它重算沒有分譜的標記）：
  - 移動聲部（`move_instruments`）：分譜跟著各自的聲部走；沒有分譜的聲部移到哪裡都仍是本專案有、沒有分譜
  - 單獨排分譜（`reorder_files`）：樂器表不動，接分譜的聲部依序配新順序的分譜，只改配對
  - 改名（`rename_instrument`）：分譜留在原位，跟著改名後的聲部；「本專案有」不變
  - 取消勾選（`set_present(…, False)`）：它的分譜移到未分組尾端，回傳移走的分譜。重新勾選的聲部沒有分譜，也不接多出的分譜
  - 新增聲部（`add_instrument`）：有多出的分譜時配第一份，沒有時沒有分譜
  - 移除聲部（`remove_instruments`）：被移除的聲部的分譜移到未分組尾端，其他的不動，回傳移走的分譜
  - 分譜拿出群組（移到未分組、搬到別的群組、設為總譜、刪除引用）：配到它的聲部沒有分譜。分譜進入群組（`add_files`、`move_to_group`、設為總譜時換下的總譜）：先配給本專案有、還沒有分譜的聲部（依樂器表順序），不夠配的接在最後。清除總譜（`clear_score`）照舊插在分譜最前面，依位置配對
  - 整份換掉樂器表（`set_instruments`）與分割的結果（`apply_split`）照位置配對，每個聲部都有。復原分割時連同「本專案有」與沒有分譜退回（`SplitPlacement.present`、`SplitPlacement.vacant`；紀錄的是合併譜拿出群組之前的編制，放回合併譜後配對與分割前相同）

### 人數與時長

- 人數是群組層級：樂器表逐列帶人數範圍（`Group.headcounts`，`Headcount(minimum, maximum, open_ended)`，與 `instruments` 逐列對應，存進專案檔），所以整首與各樂章分開記。改它只經 `set_headcount(group, index, headcount)`
- 寫入前經 `Headcount.normalized` 整理：最少留空（None，0 也算）＝未填；最多留空＝等於最少，最多不大於最少時也留空；「以上」沒有最多。`text()` 是 HuaXia 的記法（`6`、`6-8`、`2↑`，未填為空字串），`filled` 判斷有沒有填最少。人數可以先不填，分割與重新命名不檢查；只有發譜要求填最少
- 人數跟著聲部：移動、取消勾選、移除其他列、改名都留在原本那個聲部（`_VoiceRow` 連同人數一起重排）；新增的聲部未填。整份換掉樂器表（`set_instruments`、分割的結果）時，與原樂器表同一聲部的列沿用原本的人數，其餘未填；復原分割時連同人數退回（`SplitPlacement.headcounts`）
- 時長也是群組層級，以秒存（`Group.duration_seconds`，None 為未填，0 也算未填），改它只經 `set_duration`；`format_duration` 寫成「分:秒」（例如 `7:05`）
- 複製編制（`copy_instrumentation(group, source)`）：群組的每個聲部以同一聲部的規則對到來源群組的一列，複製它的人數；對應不到的留空（回傳這些聲部），來源有重名時取第一列。聲部組是專案層級、以樂器為鍵的對照，同一專案的群組本來就共用，所以不必另外複製

### 樂團類型與聲部組

- 樂團類型（`Project.orchestra_type`，`OrchestraType`）是專案層級：國樂團（吹管、拉弦、彈撥、打擊、低音）或管弦樂團（木管、銅管、打擊、鍵盤、弦樂），兩套都另有「其他」（`ORCHESTRA_SECTIONS`）。新專案是國樂團；主視窗底部的「樂團類型」選單以 `set_orchestra_type` 改它。專案裡存的是 `OrchestraType`，只在 `to_data`、`from_data` 與值互轉；專案檔的值不認得（較新版本才有的類型）時開成國樂團
- 聲部組對照（`instrument_sections`）以樂器為鍵：同一樂器（`core/voice_names.py` 的 `instrument_key`，去掉結尾編號）的各個聲部共用一個值，鍵保留第一次寫入的寫法。改聲部組一律經 `set_section(voice, section)` 或 `update_sections(sections)`，同一樂器已有鍵就改它的值；`set_section` 回傳專案裡跟著改的其他編號，`same_instrument_voices` 在改之前列出它們（各群組的樂器表都算，例如其他樂章；同一聲部只列一次，不列聲部本身），編制表寫在選單旁（例如「二胡 II 也會跟著改」）
- 值一律是中文的聲部組名稱，介面為英文時只在顯示時換成英文（`SECTION_NAMES_EN`）
- 沒有存值的樂器依樂團類型以關鍵字偵測（`core/sections.py` 的 `detect_section`、`SECTION_KEYWORDS`）：國樂團的胡類歸拉弦，大提琴、低音提琴、革胡歸低音，偵測不到的歸「其他」。`section_of` 取存值或偵測值；改樂團類型時已存的值不變，只有沒存的改依新的那套偵測
- 選單的選項是專案樂團類型那一套（`section_options`）；已存的值不在選項裡時另外列出

### 連到譜庫

群組可以連到譜庫裡的一處：一個版本的整首或其中一個樂章（ADR 0002：連上後編制與時長以譜庫為定本，專案只存快照）。

- 連線記在群組（`Group.catalog_link`，`CatalogLink`）：版本 ID、樂章 ID（整首為空字串）、給群組面板顯示的曲名、版本標示與樂章名稱，以及那處的快照（`CatalogSnapshot`：聲部與人數、時長、社團對照裡群組各樂器的聲部組）。存進專案檔，屬於格式 3；沒連線的群組存 `null`
- 讀那處經 `CatalogService.read_place`（兩次請求）；找不到時以 `CatalogService.create_place` 新建還沒有的曲目（作曲家以名稱找已有的，沒有就新增）、版本（在譜庫根資料夾下以預先要到的 ID 建同曲名的 Drive 資料夾，回應沒收到而重送時取已建好的那個；新曲目以它為使用中的版本）與樂章（群組的樂章編號與名稱），建好一部分就記在 `PendingPlace`，失敗後以同一個物件重送只補上缺的
- 譜庫的結構只在既有工作表後面加欄、另開新工作表（欄位常數在 `core/catalog_constants.py`）：分譜工作表加人數三欄（最少、最多、是否「以上」）與總譜標記欄，另有「時長」（每個版本 × 樂章或整首一列，記秒數）與「聲部組對照」（樂團類型、樂器 → 聲部組）。這些欄與工作表不存在時讀成空的；同一聲部（或同一樂器）有兩列時只認排在前面那一列，總譜列不算聲部
- 連線是編輯操作 `Project.link_group(group, place)`，依兩邊有沒有編制分三種：
  - 譜庫那處還沒有任何聲部：不問，群組的編制留著，下次存檔寫進去
  - 群組還沒有樂器表：樂器表與人數換成譜庫的。分譜以檔名取出聲部名稱（`extract_instruments_from_filenames`），以同一聲部的規則對到譜庫的聲部；認不出的依原順序填進剩下的聲部，結果的 `guessed` 列出這些依位置猜的聲部（編制表標黃）；聲部不夠配的分譜移到未分組（`moved`）。群組有分譜時，沒配到分譜的聲部自動為本專案沒有
  - 兩邊都有編制：沒給選擇（`LinkChoice`）時不連、群組不變，回報 `needs_merge`，交給合併差異表；整張二選一：
    - 用譜庫的（`LinkChoice.CATALOG`）：照下方的依名稱配對換成譜庫的編制，對不到的分譜在結果的 `moved`
    - 用群組的（`LinkChoice.GROUP`）：編制與配對不變，快照是譜庫的，所以兩邊的差異都成為下次存檔要寫進去的改動
- 依名稱配對（`Project.apply_catalog_voices(group, voices)`，連線的用譜庫的也走它）：每份分譜以它在樂器表的聲部名稱，以同一聲部的規則對到譜庫的聲部，新的聲部用譜庫的寫法與人數，所以群組少一個聲部、多一個聲部時後面的分譜不會整批錯位；換成譜庫的寫法會改到 `{樂器}` 與輸出檔名。樂器表沒有的聲部在群組有分譜時自動為本專案沒有；譜庫沒有的聲部，它的分譜移到未分組尾端；原本就沒配到聲部的分譜不動
- 合併差異表的內容是 `Project.merge_rows(group, place)`（不改群組）：每個聲部一列（`MergeRow`），依譜庫的順序，只在群組的聲部排在群組裡它前一個聲部之後；列出兩邊的寫法與人數、差異（`MergeDifference`：相同、人數不同、只在群組、只在譜庫）、連線後的聲部組與被社團的值蓋掉的專案的值，以及用譜庫的時配到的分譜與本專案有沒有（與實際套用的結果一致；只在群組的聲部是會移到未分組的分譜）
- 時長：譜庫有就用譜庫的；聲部組：社團對照有的樂器以社團的值寫進專案的對照（`put_section`），沒有的樂器沿用專案的值
- 樂器表有重名的列（舊專案留下的）時丟出 `DuplicateVoicesError`，`rows` 是重名的每一列，群組不變
- 待寫入的改動不另外記：`Project.catalog_changes(group)` 拿群組目前的編制、時長與聲部組跟快照比，列出聲部清單（同一聲部的另一種寫法不算）、各聲部的人數（快照沒有的聲部有填才算）、時長、各樂器的聲部組（社團對照沒有的樂器以專案的值列出）。連線讓專案變成未存檔，寫回譜庫並更新快照見下方「寫回譜庫」
- 編制表上方顯示連線（曲目 › 版本 › 樂章；整首時寫整首，版本沒有標示時寫未命名版本），沒連線時是「連到譜庫…」按鈕（`InstrumentationTable.link_requested`）。主視窗先擋下樂器表有重名的列（寫出列號與聲部），譜庫還沒設定時先開譜庫設定，再開連線對話框（`ui/catalog_link_dialog.py`）：依序挑曲目、版本、樂章或整首，各層都可選「新建」，開啟時依群組的曲名、使用中的版本與樂章編號預選；讀到的曲目清單（`CatalogService.link_targets`，一次請求）連同譜庫用過的聲部名稱，記進自動完成的候選（`VoiceCandidates.remember_catalog`），不必開譜庫視窗。連上後編制表以 `show_linked` 標黃依位置猜的聲部（換顯示別的群組時清掉）、寫出移到未分組的分譜。兩邊都有編制時，連線對話框先開合併差異表（`ui/catalog_merge_dialog.py` 的 `CatalogMergeDialog`，內容是 `merge_rows`）：按鈕「取消」「用群組的」「用譜庫的」，預設用譜庫的；選了就照它連線，取消時留在連線對話框重新挑

### 改連

連錯時改連到別處，不提供單純取消連線。改連就是再連一次（`link_group`），原本那處留著這個群組寫進去的編制，可以選擇撤掉。

- **撤得掉的**：`CatalogService.revert_rows(edition_id, movement_id, group_id, group_name, orchestra_type)`（兩次請求）讀原處與編制寫入紀錄，交給 `core/catalog_revert.py` 的 `revert_rows`：這個群組（紀錄的群組 ID 欄，同名的群組分得開、群組改名後也認得；沒有群組 ID 的舊列以「群組」欄的名稱認）在那處寫過的聲部各一列（`RevertRow`，依譜庫現在的順序），撤掉後分三種（`RevertOutcome`）：
  - 刪掉這個聲部：它新增、之後沒人改過的
  - 改回原值：它改過人數、之後沒人改過的，改回它這段寫入之前的值
  - 不動（`KeepReason`）：之後被別人（別的群組、譜庫視窗）改過，寫出最後是誰在何時改的；紀錄裡沒有、譜庫現在的值卻跟它寫的不同（在試算表上改的）；新增的聲部已登記 Drive 檔案
  - 只撤聲部的增刪與人數；順序、時長與聲部組不撤，它刪掉的聲部不加回去；它撤掉過的（紀錄的來源是撤銷）不再列。還沒有編制寫入紀錄、或那處已不在譜庫時沒有可撤的。撤銷存入的「一起撤掉編制」共用這套判斷
- **介面**：編制表上方連線旁有「改連…」（與「連到譜庫…」同樣發出 `link_requested`，版本頁不顯示），開同一個連線對話框（標題是改連），挑選或新建、合併差異表都一樣。讀那處時一併讀撤得掉的；連上後有撤得掉的才開確認框（`ui/catalog_revert_dialog.py` 的 `CatalogRevertDialog`，原型 #65 的變體 B）：「要撤掉原本那處的 N 項編制嗎？」、原處的位置、四欄表（`revert_table`：聲部、那次寫的、譜庫現在、撤掉後），按鈕「留著」「撤掉」。在合併差異表取消時不問、連線不變；連回原處時不問。撤銷存入的「一起撤掉編制」共用 `revert_table`
- **選了撤掉**：`Project.queue_catalog_revert(group, pending_revert(...))` 把撤得掉的聲部記在連線上（`CatalogLink.reverts`，`CatalogRevert`：要刪的聲部、要改回的人數連同那次寫的值），存進專案檔；再改連時留著，連回那處時丟掉
- **存檔時寫入**：`place_writes` 在群組的改動之後接著它的撤掉（`PlaceWrite.revert`）：要刪的聲部各一格（有→沒有）、要改回的人數各一格（那次寫的→原值），走寫回譜庫的同一套比對與同一個請求。譜庫已不是那次寫的值的格子不動（`Verdict.KEPT`，不算衝突、不進衝突畫面），那處已不在譜庫時整處不動；編制寫入紀錄的來源記撤銷。寫完 `mark_catalog_synced` 拿掉寫過的撤掉，不改群組與快照。寫不進去時跟改動一樣標未同步（只剩撤掉沒寫的群組也算在 `unsynced_groups`），下次存檔或開啟時重試

### 寫回譜庫

連到譜庫的群組的改動以格子為單位寫回譜庫，只送改過的格子（ADR 0002）：

- **時機**：按專案的存檔（儲存、另存新檔，也包括關閉前問是否儲存時選儲存）時，主視窗先寫回譜庫再寫專案檔（`MainWindow._write_back_to_catalog`）；沒按儲存就不寫進譜庫。沒有待寫入改動的專案不連譜庫。寫回在背景執行、期間顯示等待視窗；有衝突時開衝突畫面（`ui/catalog_conflict_dialog.py`，原型 #60 存檔衝突的變體 C），列出這次會寫進譜庫的全部改動，衝突的標紅、逐項選「用我的」或「用譜庫的」，全選完才能按「寫入並存檔」；取消就不寫譜庫也不存檔
- **寫不進去**（斷網、API 失敗）：專案檔照樣存，這次要寫的群組標未同步（見下方「未同步」）；主視窗頂端顯示提示列（「寫不進譜庫，改動標為未同步」，按「重試」再存一次）。在衝突畫面取消才不存專案檔

- **拆成格子**：`core/catalog_sync.py` 的 `place_writes(project)` 把每個群組的 `catalog_changes` 拆成 `SyncItem`：每個新增、刪掉的聲部各一格，快照與群組都有的聲部順序變了時一格，每個聲部的人數、時長、每種樂器的聲部組各一格。同一聲部的另一種寫法不算改動；改名是刪掉舊的、新增新的
- **比對**：`CatalogService.sync_instrumentation` 寫入前一刻重讀譜庫，每一格依譜庫現在的值（`review_items`）：等於這次要寫的新值為已完成（不寫、不算衝突）；等於快照的原值就寫；兩者都不是為衝突。有衝突時整次不寫，交回比對結果；衝突選邊（`Decision`，記著選的時候看到的譜庫值）後再呼叫一次，又重讀一次，選邊之後譜庫又變了的格子再列為衝突
  - 選「用我的」照寫；選「用譜庫的」不寫，寫完後群組改成譜庫的值：人數、時長、聲部組（改專案的對照）、順序（兩邊都有的聲部照譜庫的相對順序，分譜跟著聲部）；人數衝突而譜庫已刪掉那個聲部時，群組拿掉它，分譜移到未分組
  - 要刪掉的聲部在譜庫已有 Drive 檔案（分譜列登記了檔）時不寫（`BLOCKED`，無法寫回，要到譜庫視窗處理），其餘照寫
- **寫入**：一次存檔所有群組的格子、新增的列、刪掉的聲部（清空那一列，不刪列，別的列號不變）、缺的標題與編制寫入紀錄，以同一個 `values.batchUpdate` 送出，全成或全不成。請求數固定，不隨聲部數或群組數增加：列出工作表、讀取、寫入各一次，再加上還沒建立的時長、聲部組對照、編制寫入紀錄每張一次
  - 分譜列：新增的聲部接在工作表最後；有新增或順序要寫時，依群組的順序把排序欄改成 1、2、3…，只送值變了的格子；刪掉聲部不改其他列的排序欄。人數寫三欄（最少、最多、是否「以上」），只送變了的那幾格
  - 時長：那處有一列就改秒數，沒有就新增一列；聲部組：社團對照已有同一樂器就改它的值（樂器的寫法不變），沒有就以去掉編號的樂器名稱（`instrument_name`）新增一列，同一樂器在一次存檔裡只寫一次
  - 第一次寫入舊譜庫時建立需要的工作表並寫上標題列，分譜工作表補上新增的欄的標題
  - 編制寫入紀錄（`SHEET_INSTRUMENTATION_LOG`）：每一格寫入一列，記時間、操作者（登入的 email）、來源（`WriteSource`：存檔、譜庫視窗、撤銷）、版本與樂章、聲部、欄位、原值（寫入前譜庫的值）、新值、群組名稱與群組 ID（聲部組對照的寫入沒有群組）。只新增、不修改；已完成與選「用譜庫的」的格子不記
  - 寫不進去時沒有任何一格被寫入，以同樣的參數再呼叫一次即可；回應沒收到而其實已寫入時，重送的比對會把它們判為已完成
- **寫完交回專案**：`Project.mark_catalog_synced(outcome)` 套用選「用譜庫的」的值，把快照改成群組現在的編制、時長與聲部組，加上無法寫回、還留在譜庫的聲部，所以之後 `catalog_changes` 只剩無法寫回的改動。快照另記那處已有 Drive 檔案的聲部（`CatalogSnapshot.filed`）
- **已有 Drive 檔案的聲部**：在連到譜庫的群組，`remove_instruments` 與改名成別的聲部（`rename_instrument`）遇到快照記著已有 Drive 檔案的聲部時丟出 `FiledVoicesError`、樂器表不變，因為這等於從樂譜刪除；這場缺這份分譜時取消勾選「本專案有」
- **聲部組的影響範圍**：讀到那處（連線、寫回）時一併記下群組各樂器被譜庫其他曲目用到幾首（`CatalogLink.other_pieces`，`other_pieces_using(voice)` 查詢，總譜列與同一首曲目的其他版本不算）
- **譜庫視窗編輯聲部組對照**：`CatalogService.section_map` 讀出國樂團、管弦樂團兩套（`SectionMapEntry`：社團對照的樂器保留第一次寫入的寫法，接著是分譜工作表用到、對照還沒有的樂器，聲部組空白；各標出譜庫裡用到幾首，總譜列不算）。按儲存時 `core/catalog_sync.py` 的 `section_map_items` 只列改過的樂器（移回未歸類＝聲部組改成空白，讀取時當成沒有），`CatalogService.sync_section_map` 走上面同一套比對與寫入：每個樂團類型一處（`PlaceWrite.group_id` 是樂團類型的值、沒有版本），只比對社團對照，別人同時改過同一個樂器就是衝突；編制寫入紀錄的來源記譜庫視窗，版本、樂章與群組空白
  - 介面是譜庫視窗工具列的「聲部組對照」，在右側面板開 `ui/section_map_editor.py` 的 `SectionMapEditor`（原型 #60 聲部組對照的變體 B）：每個聲部組一欄、最前面是「未歸類」，以樂器為單位拖拉，欄標題寫樂器數、樂器標出用到幾首；樂團類型選單切換兩套（預設是開著的專案的），搜尋框篩選每一欄；沒有改動時不能按儲存。按儲存在背景寫入，有衝突時開衝突畫面（按鈕是「寫入」），選邊後再寫一次；寫好後重新讀取，維持原本顯示的那套。沒按儲存就換到別的曲目或關掉視窗，改動丟掉、譜庫不變

### 未同步

存檔時寫不進譜庫的群組標成未同步，斷網時照樣可以編輯、分割、重新命名與存檔。介面用詞「未同步」只用在編制，不跟存入的「未存入」共用。

- **標記**：`Project.mark_catalog_unsynced(group_ids)` 在群組的連線記 `CatalogLink.unsynced`，存進專案檔。不另存一份改動清單：未同步的值（`Project.unsynced_changes(group)`）就是標了未同步的群組待寫入的改動（`catalog_changes`），原值是譜庫最後一次讀到或寫進去的值；`Project.unsynced_groups()` 是有未同步的值的群組。標記之後又改的值，在存檔前也算在未同步裡
- **清掉**：寫回成功時 `mark_catalog_synced` 清掉標記；改回快照的值時未同步的值是空的，群組不算未同步
- **顯示**：編制表頂端（`header` 版面、連線之下，與開啟專案時聲部清單變動的提示列同一處）寫出哪些值未同步，例如「未同步：琵琶 人數、時長。下次存檔或開啟專案時再試。」；時長旁寫「譜庫現在是 3:00」，人數未同步的聲部名稱標橘色，聲部名稱與人數欄的提示寫出譜庫現在的人數
- **下次存檔重試**：存檔照常以 `place_writes` 寫回所有待寫入的改動，走同一套比對與衝突畫面
- **開啟專案時重試**（`MainWindow._retry_unsynced`，在更新快照之前）：只寫回未同步的群組，走同一套比對與衝突畫面；寫入後再存一次專案檔，清掉檔裡的標記（開啟時就有未存檔的改動時不自動存）。還是寫不進去時標記留著，頂端顯示提示列，按「重試」再試一次；在衝突畫面取消時什麼都不變。唯讀的專案不重試
- **關閉時提醒一次**：關閉程式、開新專案或開啟別的專案時，在「是否儲存」之後，專案還有未同步的群組就提醒一次（列出群組，可取消關閉）

### 開啟時更新快照

開啟專案時，連到譜庫的群組從譜庫更新快照（ADR 0002：譜庫是定本，專案只存快照）。

- **讀取**：各群組連到的那處以 `CatalogService.read_places` 一起讀（兩次請求，不隨群組數增加），交給 `Project.refresh_catalog(group, place)`。一處已不在譜庫時只有那一處讀成 None：那個群組照快照，其他群組照常更新，頂端提示列寫出是哪些群組（「…連到的那處已不在譜庫，編制照專案裡的」，按「重新讀取」再讀一次）
- **人數與時長直接套用**：譜庫的值跟快照不同時，群組還是快照的值就改成譜庫的，快照跟著改；群組另有還沒寫回的值（例如未同步）時兩邊都不動，存檔時照「寫回譜庫」的比對列為衝突
- **其他**：曲名、版本與樂章的名稱、已有 Drive 檔案的聲部（`CatalogSnapshot.filed`）、各樂器被其他曲目用到幾首換成讀到的。聲部組不在這裡更新
- **聲部清單變了**（增刪、名稱、順序）：不自動套用。譜庫的清單跟群組的一樣時快照直接換成譜庫的；不一樣時記下讀到的那處（只在記憶體，不進專案檔），`Project.catalog_list_change(group)` 回報差異（`CatalogListChange`：譜庫的清單、只在譜庫的、只在群組的、換了相對順序的聲部）。還沒決定時配對與命名照專案的清單，快照的清單也不變，所以存檔不寫清單，下次開啟再讀到同樣的差異
- **套用譜庫的**（`take_catalog_list`）：照「依名稱配對」換成譜庫的清單，對不到的分譜移到未分組（回傳這些分譜）；群組原有的聲部保留群組的人數，新增的聲部用譜庫的人數，新增的樂器在社團對照有聲部組時以社團的為準；快照的清單換成譜庫的
- **用專案的（存檔時寫回）**（`keep_project_list`）：群組與配對不變，快照的清單換成譜庫的，群組的清單因此成為待寫入的改動，並標 `CatalogLink.confirm_voices`（存進專案檔）：下次寫回的 `PlaceWrite.confirm`，寫入前先以 `sync_instrumentation(…, review_only=True)` 只比對、在衝突畫面確認全部改動再寫（沒有衝突時畫面的說明改為確認）。要刪掉的聲部在譜庫已有 Drive 檔案時無法寫回（`BLOCKED`），其餘照寫；寫回成功時清掉標記
- **主視窗**（`MainWindow._sync_catalog_on_open`，在 `_do_open_project` 最後）：先重試未同步的群組（見上方「未同步」），寫不進去就不更新，未同步的改動才不會被當成譜庫的新值；再以 `_refresh_from_catalog` 讀各處、交給專案。開啟時沒有未存檔的改動、更新後有改動（人數、時長、名稱、已有 Drive 檔案的聲部）時再存一次專案檔，所以只是開啟不會讓專案變成未存檔；聲部清單還沒決定時不改專案檔的內容。讀不到時照快照開啟、不擋編輯，頂端顯示提示列（「讀不到譜庫，編制照專案裡的」），按處理按鈕再讀一次。唯讀的專案不更新
- **編制表**：聲部清單變了的群組，頂端（`header`，未同步的提示列之下）出現提示列，按鈕「套用譜庫的」「用專案的（存檔時寫回）」各呼叫上面兩個操作；表格標出譜庫已移除的列（紅底）與換了相對順序的列（藍底，提示寫出譜庫裡排第幾個），譜庫新增的聲部以綠底、不能勾選、編輯、選取或拖動的列接在最後。選了用專案的之後，提示列換成「存檔時會把這份聲部清單寫回譜庫，寫入前先確認」，寫回成功後收起

### 版本頁

譜庫視窗的版本頁顯示譜庫裡一處（版本的整首或一個樂章）的編制與登記的檔，把版本資料夾裡還沒登記的 PDF 登記到聲部上：

- **讀取**：`CatalogService.edition_page(edition_id, movement_id, orchestra_type)` 回傳 `EditionPage`：那處（同 `read_place`）、登記了 Drive 檔案的聲部與登記的檔（`registration(voice)`）、總譜列登記的檔、沒登記的檔（`FolderPdf`，帶在版本資料夾裡的路徑），以及版本資料夾裡全部的 PDF（`pdfs`，一般下載從這裡挑）。試算表兩次請求，再每個資料夾列出一次
- **狀態由登記推算**：分譜列登記了 Drive 檔案（`drive_file_id`）就是有，沒有就是缺；不讀也不寫舊的 `status` 欄
- **沒登記的檔**：版本資料夾與它所有層的子資料夾裡、沒被任何分譜列（不分版本與樂章，含總譜列）登記的 PDF；垃圾桶裡的不算
- **登記**：`CatalogService.register_files(PendingRegistration)` 寫入前一刻讀分譜工作表找列號，聲部與總譜列的登記（`drive_file_id`、`file_name`）以一個請求寫入；那處還沒有總譜列時新增一列（標記總譜欄，沒有人數）。要登記的聲部已不在譜庫時為已經不在譜庫
  - 換掉已登記的檔時，登記寫好之後才把原本那份丟進 Drive 垃圾桶（`DrivePort.move_to_trash`，約 30 天內可救回）；中途失敗時以同一個 `PendingRegistration` 重送，已寫好的登記不再寫，還沒丟的舊檔接著丟
- **畫面**：`ui/edition_page.py` 的 `EditionPagePanel`，是譜庫視窗曲目的「編制與分譜」頁籤（原型 #60 版本頁的變體 A）。上方選版本（預設使用中的版本）與樂章或整首，下面兩欄：
  - 左欄是主視窗同一個編制表（`InstrumentationTable(edition_page=True)`）：多了狀態與登記的檔兩欄（`show_files`，唯讀，不能手改；指定了還沒儲存的寫成待儲存），最上面固定一列總譜（沒有人數、聲部組），沒有本專案有、從其他群組複製與從檔名擷取。編制表顯示的是只在這一頁的專案：一個以 `link_group` 連到這一處的群組，快照就是讀到的那處，所以編制表的改動就是待寫入的改動
  - 右欄是沒登記的檔：選一個檔、再選左邊的聲部或總譜列（`selected_target`），按「指定」。那裡已登記了檔時先問，寫明原本那份按儲存後會丟進 Drive 垃圾桶、30 天內可救回；指定給已不在聲部清單裡的聲部的檔放回右欄
  - 按「儲存」才寫進譜庫：編制的改動走寫回譜庫的同一套比對（`place_writes`、`sync_instrumentation`，編制寫入紀錄的來源是 `WriteSource.CATALOG_WINDOW`），有衝突時開同一個衝突畫面選邊（按鈕是「寫入」）；沒有待選邊的衝突才登記指定的檔，寫完重新讀取。「放棄改動」與換版本、樂章、樂團類型時重新讀取；有沒儲存的改動時先問「放棄還沒儲存的改動？」，選否就留在原處（選單退回原本的）。刪除已登記 Drive 檔案的聲部時說明「已登記 Drive 檔案，不能刪除」（主視窗的說明另外請到譜庫視窗處理）
  - 套用命名格式與「下載…」（一般下載，見從譜庫下載）的按鈕在選單下方（`EditionPagePanel.actions`），存入紀錄的入口也放這一列
  - 樂團類型（聲部組對照取哪一套）預設是開著的專案的（主視窗開譜庫視窗時傳入），選單在樂章選單旁，可以切換

### 存入譜庫

已重新命名、已連到譜庫的群組的總譜與分譜，上傳到那個版本的 Drive 資料夾並登記到分譜工作表的聲部；本機那份不動。預覽（`DepositService.preview`）與執行（`DepositService.deposit`）在 `services/deposit_service.py`，每份檔的動作在 `core/deposit.py`，碰譜庫經譜庫服務（`place_files`、`deposit_log`、`drive_ids`、`begin_deposit`、`upload_file`、`update_file`、`place_file`、`record_deposits`）：

- **能存入的群組**（`deposit_sources`）：連到譜庫、而且已重新命名＝總譜與每份配到聲部的分譜都在命名格式算出的位置（有輸出位置時比整條路徑，就地改名時比檔名與上層資料夾，不分大小寫）。其餘整個群組不存入（`DepositBlock`：沒連到譜庫、還沒重新命名、沒有檔、有本機找不到的檔、檔都只在譜庫、版本沒有 Drive 資料夾、連到的那處已不在譜庫）。讀各處的登記（`CatalogService.place_files`，存入、清除與下載回原位共用）時一處已不在譜庫只少那一處，其他群組照常。只在譜庫的檔（見下方「只在譜庫」）跳過，群組其餘的照常存入；只在譜庫以外的找不到才擋下整個群組。多於聲部數的分譜不改名，也不存入
- **放在 Drive 的哪裡**：版本資料夾就是群組的資料夾，底下的子資料夾與本機相同；開啟子資料夾輸出時，群組那一層不帶到 Drive，分譜資料夾、聲部組資料夾照帶。還沒有的子資料夾以預先要到的 ID 建立
- **每份檔的動作**（`DepositAction`，比對都以 Drive 的 `md5Checksum` 與本機的 MD5）：
  - 聲部已登記了 Drive 上還在的檔：內容、檔名與資料夾都相同就跳過；只有檔名或資料夾不同就搬移；內容不同就以 `files.update` 換掉同一個檔的內容（ID 不變，舊內容成為 Drive 的版本），同一個請求裡改名、搬移
  - 聲部沒登記，但目標資料夾有沒登記給任何一列的同名檔：內容相同就直接登記，不同就更新它的內容後登記
  - 都沒有：以預先向 Drive 要的 ID 上傳（`files.generateIds`，一次最多 1000 個，多的分幾次要；大檔用 resumable 上傳）。回應沒收到而重送時 Drive 回已經存在（409），譜庫服務取那一份，不產生第二份
  - 那處的分譜工作表沒有這個聲部（還沒寫回編制）：不存入。總譜登記在那處的總譜列（`is_score`），還沒有就新增一列（聲部名稱留空，同版本頁的登記 `register_files`）
- **先寫「要做」**：動 Drive 之前，新上傳的檔與還沒有的子資料夾先一起要好 ID，再以一次試算表寫入替每份要做的檔寫一列「要做」的存入紀錄（`CatalogService.begin_deposit`，狀態欄是 `DEPOSIT_PENDING`：要動的 Drive 檔案 ID（新上傳是預先要到的）、動作、被蓋掉的版本 ID，沒有寫入後的版本）。這一列寫不進去就不動 Drive
- **登記與存入紀錄**：一份一份做完 Drive 上的事之後（取消、中途失敗時也是，只算已做完的），以一次試算表寫入登記全部的分譜列（寫入前一刻才讀列號，只送值變了的 `drive_file_id`、`file_name`），並每份檔寫一列做了的存入紀錄（`record_deposits`，`SHEET_DEPOSIT_LOG`：存入編號（與「要做」列同一個）、時間、操作者、版本與樂章、群組名稱與群組 ID、聲部、本機路徑、Drive 檔案 ID、動作、寫入後與被蓋掉的 Drive 版本 ID），只新增、不修改。登記寫不進去時，蓋掉的內容只有「要做」列：撤銷存入照 Drive 現況判斷那次做到了沒有（見下方「撤銷存入」），所以每一次蓋掉內容都撤得掉。代價是試算表多一次寫入（列出工作表、讀、寫各一次），存入紀錄每份檔多一列；請求數仍固定（預覽讀登記一次、讀存入紀錄兩次；「要做」與登記各列出工作表、讀、寫一次，存入紀錄還沒建立時另建一次），不隨聲部數增加；Drive 的請求每份檔一次（跳過的不送）
- **中斷後重按就補齊**：重新預覽時已登記且內容相同的跳過；上傳了但還沒登記的（登記沒寫進去）是目標資料夾裡的同名檔，內容相同就直接登記。登記寫不進去時這次做好的都不算完成
- **上次中斷的提示**：預覽時讀存入紀錄（`deposit_log`），這個專案的群組（群組 ID，舊列以名稱認）最近一次存入有只寫了「要做」列的檔，就是上次中斷（`DepositPlan.interrupted`，`core/deposit_revert.py` 的 `interrupted`：那次做了幾份）。從譜庫推算，所以程式重開、換一台電腦也看得到；重按補齊之後就沒有
- **存入指紋**：存進去的每份檔記下譜庫裡那份內容的 MD5（`FileInfo.deposit_md5`，存進專案檔；沒存入過的檔不寫這個鍵），經 `Project.record_deposit(records)`；同時把這些聲部加進快照的 `filed`，連到譜庫的群組不能再從樂器表刪掉它們。之後拿本機檔案的 MD5 比對它，就知道本機改過、還沒重新存入
- **未存入**（`DepositService.undeposited(project)`）：存入過（有存入指紋）的檔，本機檔案的 MD5 跟指紋不一致就是未存入；內容改回存入時的樣子就不算。只讀本機檔案、不連網，本機找不到的檔不算。大小與修改時間沒變的檔沿用上次算的 MD5（`FileService.stamp`），重畫群組面板不必每份重讀。介面用詞「未存入」只用在存入，不跟編制的「未同步」共用。復原重新命名時 `replace_paths` 換的是同一個檔案資訊的路徑，指紋跟著走，所以復原後內容沒變的檔不算未存入
  - 群組面板（`GroupTab.show_undeposited`）：未存入的分譜與總譜改用橘字，檔案清單上方寫「本機較新，還沒存入譜庫：琵琶.pdf」。重建分頁、切換分頁與切回視窗時重新比對（檔可能在別的程式裡改過）
  - 關閉時提醒一次（`MainWindow._confirm_undeposited`）：關閉程式、開新專案或開啟別的專案時，在未同步的提醒之後，專案還有未存入的檔就提醒一次（列出群組，可取消關閉）
  - 復原存入過的重新命名照常完成，再提示譜庫裡的那份維持原樣（見 [move-history.md](move-history.md) 的復原與重做）
- **主視窗**：「譜庫」選單的「存入譜庫…」先在等待視窗裡讀出計畫，再開預覽（`ui/deposit_dialog.py`，原型 #65 存入的變體 C）：左邊群組清單寫出各動作的份數，不存入的寫原因，沒連到譜庫的附「連到譜庫…」；右邊是所選群組的「聲部／本機 → 譜庫（Drive）／動作」，預設只看要上傳或搬移的；上方是未存檔時的紅色提示（「存入譜庫」按不下去）與上次中斷的提示（`DepositPlan.interrupted`），底部是合計。專案沒存過檔或有未存檔的改動時不能存入
- **進行中**：在背景執行（`MainWindow._run_in_background`），狀態列顯示進度與取消；期間鎖住專案編輯、存檔、重新命名、分割、復原與重做，分頁仍可瀏覽。取消時做完目前這一份就停，已完成的保留。結束後把存入指紋交回專案並自動存檔一次（只存下指紋，不經寫回譜庫）；中途失敗時頂端的提示列寫出已完成幾份、重按就補齊，按「重試」再開一次存入。存入的每份檔也寫一筆紀錄檔

### 清除本機檔案

確認譜庫裡有內容相同的一份之後，永久刪掉本機的總譜與分譜，連同清空後變空的資料夾。預覽（`ClearLocalService.preview`）與執行（`ClearLocalService.clear`）在 `services/clear_local_service.py`，每份檔的歸類與要刪的資料夾在 `core/clear_local.py`，讀譜庫各處登記的 Drive 檔沿用存入的 `CatalogService.place_files`：

- **核對**（`classify`）：本機算 MD5，跟那處這個聲部（總譜為總譜列）登記的 Drive 檔的 `md5Checksum` 比對，一致才可清除。內容不一致是「跟譜庫裡的不一樣，請先重新存入」；沒登記、登記的檔已不在 Drive、在垃圾桶裡或不在版本資料夾裡（`PlaceFiles.holds`；例如別人分享進來、擁有者刪得掉的檔）是「譜庫裡沒有」，連到的那處已不在譜庫時群組的檔都是（其他群組照常清除）；群組沒連到譜庫、分譜沒配到聲部是「還沒存入」。本機已經沒有的檔是只在譜庫（見下一節）或找不到
- **斷網**：預覽讀不到譜庫就丟出 `CatalogError`，什麼都不刪
- **只刪勾了的群組裡可清除的**：沒有可清除檔案的群組不能勾（`GroupClear.choosable`）；刪之前一刻重讀譜庫那幾處的登記與 Drive 上的檔，再照同一套核對，預覽之後登記換了、Drive 上那份改過或丟進垃圾桶的不刪（`ClearOutcome.catalog_changed`），重讀不到時什麼都不刪（`ClearOutcome.error`，主視窗頂端顯示提示列）；每份刪之前再算一次本機 MD5，預覽之後內容變了的不刪（`ClearOutcome.changed`），刪不掉的記在 `failed`，都不丟出。要求取消時做完目前這一份就停
- **永久刪除**：經 `FileService.delete_permanently`，不進資源回收桶；這是泠靈唯一的永久刪除，其他刪除照舊走資源回收桶。不放上復原堆疊。清除的每份檔寫一筆紀錄檔
- **空資料夾**（`emptied_folders`）：清空後變空的資料夾由內而外往上刪到輸出位置為止（輸出位置本身也刪），還有東西的不刪。輸出位置是專案的輸出位置；沒指定輸出位置（就地改名）、檔案在命名結果的位置時，是路徑去掉命名結果的資料夾與檔名，也就是重新命名前來源檔所在的資料夾；其餘是檔案所在的資料夾。家目錄、磁碟根目錄與標準使用者資料夾（家目錄下英文名稱的桌面、文件、下載、音樂等，`STANDARD_USER_FOLDER_NAMES`，加上建構時傳入的系統在地化名稱）碰到就停下，它與它的上層都不刪
- **指紋**：清除的每份檔交回譜庫那份的 MD5（`ClearOutcome.fingerprints`），經 `Project.record_fingerprints` 記成存入指紋，沒經過泠靈存入、只在版本頁登記的檔清除後也認得出只在譜庫
- **主視窗**：「譜庫」選單的「清除本機檔案…」先在等待視窗裡核對出計畫（讀不到譜庫時頂端顯示提示列、不開預覽，按「重試」再開一次），再開預覽（`ui/clear_dialog.py`，原型 #65 清除的變體 C）：上方是群組總表，每個群組一列，欄位是可清除、跟譜庫不一樣、還沒存入、譜庫裡沒有的份數與可釋放的大小，群組前面勾選（能勾的預設勾著），已清除的群組是灰色一列「已清除，只在譜庫」；點一列在下方顯示這個群組的檔案明細，預設只看不能清除的；底部寫出勾了幾個群組、會永久刪除幾份、多大。專案沒存過檔或有未存檔的改動時上方紅色提示、按不下去（清除後要把指紋存進專案檔）。按下後先跳確認框：標題「永久刪除 N 份檔案？」，內文寫出哪些群組、幾份、多大、不進回收處、清空的資料夾一併刪除，以及要找回就在群組裡按「從譜庫下載回來」；按鈕「取消」「永久刪除」
- **進行中**：同存入譜庫，在背景執行（`MainWindow._run_in_background`，`locks_project`），狀態列顯示進度與取消，期間鎖住專案編輯、存檔、重新命名、分割、復原與重做。結束後把指紋交回專案，有改到就只存專案檔，重畫分頁；預覽之後改過或刪不掉而沒刪的檔列出來

### 只在譜庫

本機沒有這份檔、但群組記著它在譜庫裡有一份時，這份檔「只在譜庫」，不算找不到的檔案：

- **推算，不另外存**：群組記著它在譜庫裡有一份＝群組連到譜庫、它是群組的總譜或分譜、記著存入指紋（`Group.has_catalog_copy`，不必連網）。再加上本機找不到就是只在譜庫，每次照磁碟現況推算（`Project.catalog_only_paths(missing)`，呼叫端查好哪些檔找不到；UI 一律經 `DepositService.catalog_only(project, paths)`，它查本機在不在再交給專案）；檔案用任何方式放回原位就恢復正常
- **開啟專案**：`ProjectAccess.open` 的 `missing_files` 不含只在譜庫的檔，另列在 `catalog_only_files`，開啟時不提醒
- **群組分頁**：只在譜庫的總譜與分譜在名稱後標「（只在譜庫）」，檔案清單上方寫出有幾份只在譜庫（`GroupTab.show_undeposited` 跟未存入一起，在重畫與切回分頁或視窗時照磁碟現況推算），旁邊有「從譜庫下載回來」（見下一節）
- **重新命名**：跳過並在預覽另列一則說明（`RenameProblem.CATALOG_ONLY`，見 [move-history.md](move-history.md) 的問題的種類），說明旁有「從譜庫下載回來」
- **存入譜庫**：跳過（見上方「存入譜庫」）
- **清除本機檔案**：歸成只在譜庫；群組的檔都只在譜庫時，預覽寫成「已清除，只在譜庫」

### 從譜庫下載

只在譜庫的檔下載回原位，或把版本資料夾的檔下載到自選的資料夾。要下載哪些檔、放哪裡在 `core/catalog_download.py`（`restore_items`、`folder_items`），下載與核對在 `services/download_service.py` 的 `DownloadService`，碰譜庫經譜庫服務（`place_files` 讀那處的登記、`download_file` 下載內容）：

- **同一套下載與核對**：每份先下載到暫存資料夾（使用者資料目錄的 `temp/`，見 [data-storage.md](data-storage.md)），以 Drive 的 `md5Checksum` 核對暫存檔，一致才搬到要放的位置（資料夾不在就建）；不一致（`mismatched`）、下載中斷或取消時暫存檔丟掉，要放的位置不留半份檔案。讀不到譜庫或下載失敗時停下，已下載的保留，錯誤記在 `error`；要求取消時做完目前這一份就停。再按一次就補齊。下載的每份檔寫一筆紀錄檔，不放上復原堆疊
- **下載回原位**（`restore_sources` 在主執行緒找出群組裡只在譜庫的檔，`restore` 在背景下載）：下載的是群組連到的那處現在登記給這個聲部（總譜為總譜列）的 Drive 檔，放回清除前的路徑與檔名（`FileInfo.original_path`，清除沒有改它）。清除之後又重新存入過時下載的就是最新的，交回的指紋（`DownloadOutcome.fingerprints`）是那份的 MD5，經 `Project.record_fingerprints` 換掉記下的存入指紋。原位置已經有內容相同的檔算已經放回去；有別的檔時不覆蓋，列在 `occupied`。那處已經沒登記、那處已不在譜庫、或登記的檔已不在 Drive、在垃圾桶裡的列在 `unavailable`，其他群組照常下載
- **一般下載**（`download`）：整個版本保留版本資料夾底下的子資料夾，只勾幾份時都放在自選的資料夾裡。Drive 上的資料夾名稱與檔名照檔名清理的規則換掉非法字元，「.」「..」換成底線，放的位置不會跑出自選的資料夾。目的資料夾已有同名檔時，內容相同就略過，不同就照重新命名的規則加「 (1)」後綴（`core/filename.py` 的 `numbered`），加了後綴的那份已經有、內容也相同時一樣略過，所以再按一次不會多出一份；絕不覆蓋
- **一般下載的入口**：譜庫視窗版本頁的「下載…」開挑選視窗（`ui/catalog_download_dialog.py` 的 `CatalogDownloadDialog`），列出版本資料夾裡全部的 PDF（`EditionPagePanel.folder_pdfs`），預設勾「整個版本（保留子資料夾）」；取消它可以逐份勾選。按「下載」後選資料夾，在背景下載（`CatalogWindow._run_download`，經主視窗同一套 `TaskSlot`，下載服務是主視窗那一份），狀態列顯示進度與取消鈕，一次一件，關閉視窗時下載進行中先問要不要取消。結束後狀態列寫出完成幾份，沒下載好的依原因列出；中途失敗時頂端提示列寫出已完成幾份，按「重試」以同樣的檔再下載一次（已下載的略過）
- **下載回原位的入口**：群組分頁有只在譜庫的檔時出現「從譜庫下載回來」（`GroupTab.download_requested`），作用於這個群組；重新命名預覽說明跳過只在譜庫的檔時，旁邊也有這個按鈕（關掉預覽，作用於這次要重新命名的群組）。兩者都經 `MainWindow.download_back(group_ids)`，發譜預覽也可以逐群組呼叫。同存入在背景執行（`_run_in_background`，`locks_project`），狀態列顯示進度與取消，期間鎖住專案編輯、存檔與檔案操作。結束後把指紋交回專案（`record_fingerprints`），開始前沒有未存檔的改動時只存專案檔；目前的群組分頁照磁碟現況重新比對（停在原本的分頁），沒放回去的檔依原因列出（`ui/widgets.py` 的 `not_downloaded_text`）。讀不到譜庫或下載到一半失敗時頂端顯示提示列，寫出已完成幾份，按「重試」再下載一次

### 撤銷存入

存錯版本或樂章時，從存入紀錄挑一次存入、再挑其中的群組，撤掉那次的結果。每份檔的下場在 `core/deposit_revert.py`（`revert_preview`），讀譜庫與照決定去做在 `services/deposit_revert_service.py` 的 `DepositRevertService`（`preview`、`revert`），碰譜庫經譜庫服務（`deposit_log`、`revert_reading`、`trash_file`、`restore_revision`、`record_revert`）：

- **一次存入**（`deposits`）：存入紀錄依存入編號分成一次一次的存入，撤銷存入也是一次（`reverts` 欄記被撤銷的存入編號），新的在前。同一份檔有「要做」列也有做了的列時以做了的為準；只有「要做」列的檔（中途停下或登記寫不進去）照 Drive 現況判斷（`_settled`）：新上傳的以預先要到的 ID 找得到檔就是做到了，寫入後的版本是那個檔的第一個版本；更新內容的，目前版本不是被蓋掉的版本時，Drive 的版本裡緊接在被蓋掉的版本之後的就是寫入後的版本；只登記的沒寫進登記就是沒做到。沒做到的不動（中斷沒做到）
- **群組**：存入紀錄的一列屬於哪個群組以群組 ID 欄認（同名的群組分得開，群組改名後也認得）；沒有群組 ID 的舊列以「群組」欄的名稱認
- **只撤內容還跟那次寫入一樣的部分**：Drive 檔案目前的版本 ID（`headRevisionId`）仍是那次寫入的版本（存入紀錄的 `revision_after`）才撤；動 Drive 之前一刻再重讀那份檔，版本或垃圾桶狀態跟預覽時不同的不動，列在 `RevertOutcome.changed`
  - 那次新上傳的（`TRASH`）：移除分譜列的登記，檔丟進 Drive 垃圾桶（不永久刪除，30 天內可救回）；上次撤銷已丟進垃圾桶、登記沒寫進去的，只補移除登記
  - 那次更新內容的（`RESTORE`）：被蓋掉的舊版本（`revision_before`）Drive 還留著就還原：把那個版本設成 `keepForever`、下載並以版本的 MD5 核對，再以 `files.update` 傳回同一個檔（檔案 ID 與登記不變）；傳回後舊版本的內容已是目前的內容，把 `keepForever` 改回 false（改不回去不影響還原）。舊版本已被 Drive 清掉的列為無法還原（`LOST`），不動
  - 那次登記的是 Drive 上原有、內容相同的同名檔（`UNREGISTER`）：只移除登記，檔不動
  - 不動（`KeptBecause`）：已經撤銷過、之後又存入過（存入紀錄裡之後還有動到這個檔的做了的列，跳過的不算，連同那次的時間列出）、之後 Drive 上的內容改過、Drive 上已沒有或在垃圾桶裡、那次只改了檔名或位置、那次跳過、那次中斷沒做到
- **不毀掉唯一的一份**（`RevertBlock`，`RevertGroup.block`）：要丟進垃圾桶或還原的檔，Drive 上那份可能是那次存入內容唯一的一份。群組要在開著的專案裡（`LocalProject`：專案的群組 ID，舊列以群組名稱認），而且每份這樣的檔本機都有（內容不論，存入之後改過的也照常撤銷），或本機已清除、會先下載回原位並核對 MD5；不然整個群組不撤銷：存入時的專案沒開著是「請先開啟存入時的專案」（`NOT_OPEN`），本機找不到、又不是已清除的是 `NO_LOCAL_COPY`（`RevertGroup.uncovered` 列出是哪些）。預覽時看本機有哪些檔，撤銷時（下載回原位之後、動 Drive 之前）再看一次，預覽之後不見的群組也不撤銷（`RevertOutcome.refused`）。只移除登記的檔不動 Drive，不必有本機那份
- **本機已清除的群組**：要撤銷、本機已清除（只在譜庫，主視窗以 `DepositService.catalog_only` 判定）的檔，先以從譜庫下載的同一套做法（`DownloadService.put_back`）下載回原位並核對 MD5，再動 Drive 上的那份。有任何一份沒放回去（下載失敗、MD5 不符、原位有別的檔），這個群組就不撤銷，交回那次下載的結果當原因（`RevertOutcome.skipped`），其他群組照常
- **一起撤掉編制**（每個群組一個勾選，預設不勾）：沿用改連的判斷（`core/catalog_revert.py` 的 `revert_rows`），只看那次存入之前這個群組寫進那處的編制（`until`），之後它自己或別人的寫入都算之後被改過；這次會移除登記的聲部不算已登記 Drive 檔案，所以那次新增、連同分譜一起存入的聲部也撤得掉。寫入走寫回譜庫的同一套比對（`core/catalog_sync.py` 的 `revert_write`，與改連存檔時共用），編制寫入紀錄的來源記撤銷
- **紀錄**：Drive 上的事逐份做完後（取消、中途失敗時也是，只算已做完的），以一次試算表寫入移除登記（只清那次存入的那處、那個聲部或總譜列登記這個檔的列，同一個檔另外登記在別處的不動），並每份撤掉的檔寫一列存入紀錄（新的存入編號，動作是 `RevertAction` 的值，寫入後與之前的版本 ID，`reverts` 記被撤銷的存入編號）；只新增、不修改。編制的撤掉另是編制寫入紀錄的新列。撤掉的每份檔也寫一筆紀錄檔
- **指紋**：下載回原位的檔交回指紋（`RevertOutcome.fingerprints`，經 `Project.record_fingerprints`）；撤掉的檔譜庫不再有這份內容，經 `Project.forget_deposits` 拿掉存入指紋
- **入口**：譜庫視窗版本頁的「存入紀錄…」（`CatalogWindow` 建立時拿到撤銷的執行者 `DepositReverter`，也就是主視窗，才有這個按鈕）讀存入紀錄，列出動到這個版本的每次存入與撤銷存入（`ui/deposit_revert_dialog.py` 的 `DepositLogDialog`，撤銷存入灰字、不能再撤）。選一次存入按「撤銷存入…」，主視窗記下開著的專案（`MainWindow.revert_reader`：群組、只在譜庫的檔與樂團類型，預覽與執行用同一個樂團類型）後在背景讀出預覽，開預覽對話框（`DepositRevertDialog`，原型 #65 撤銷的變體 A）：左邊勾群組（寫出連到哪裡；只有一個群組時預設勾著，不撤銷的群組灰字、不能勾），右邊是所選群組的頁面：不撤銷時一列紅色寫出原因，各下場份數、本機已清除時的藍色提示（先下載幾份回原位並核對）、逐聲部的「現在譜庫裡 → 撤銷後 → 原因」，下面是「一起撤掉這個群組寫進某處的編制（N 項）」勾選框加四欄編制清單（與改連共用 `revert_table`），預設不勾、沒有撤得掉的時候不能勾；底部註明移除的檔放進 Drive 垃圾桶、30 天內可救回
- **進行中**：按「撤銷存入」後交給 `MainWindow.revert_deposit`，同存入在背景執行（`_run_in_background`，`locks_project`），主視窗狀態列顯示進度與取消，期間鎖住專案編輯、存檔與檔案操作；主視窗已有背景工作時不開始、說明原因。結束後把指紋交回專案，開始前沒有未存檔的改動時只存專案檔，群組分頁照磁碟現況重新比對；譜庫視窗中途失敗時頂端提示列寫出已撤掉幾份、按「重試」再讀一次預覽，沒撤銷的群組與預覽之後在 Drive 上改過的檔依原因列出（`skipped_text`），版本頁重新讀取

### 對到 HuaXia 曲目

一個群組對一首 HuaXia 曲目（spec #82）：整首群組在 HuaXia 就是一首曲目，要照「一個樂章一首曲目」排人就每個樂章各開一個群組。

- 對應記在群組（`Group.huaxia_link`，`HuaXiaLink`），存進專案檔：曲目編號（`pieces.id`）、給群組面板顯示的曲名，新建時另記新建的欄位（`NewHuaXiaPiece`：曲名、作曲家、時長分鐘數、合奏或絲竹）。不記登入資訊；沒對到的群組存 `null`。新建曲目的編號在發譜一開始才產生並寫進專案，之前為空字串
- 寫入經編輯操作 `Project.set_huaxia_link(group, link)`，由發譜預覽的「曲目」步呼叫：每個沒被擋下的群組選「挑選現有」（沒封存的曲目）或「新建」，選了就寫進專案（專案變成未存檔）；開啟預覽本身不改專案
- 編制表上方在譜庫連線之下顯示對到的 HuaXia 曲目（新建的寫明發譜時新建）
- 發譜預覽「聲部」步手動挑的配對也記在這裡（`HuaXiaLink.part_ids`：泠靈的聲部名稱對應 HuaXia 的聲部編號 `piece_parts.id`），經編輯操作 `Project.choose_huaxia_part(group, voice, part_id)` 寫入，`part_id` 為 None 是改回新建、忘掉記過的配對；名稱規則對上的不記。查詢經 `HuaXiaLink.part_for(voice)`，以同一聲部的規則比對名稱，所以泠靈改了寫法（「二胡 I」改成「二胡1」）照樣找得到；記的是編號，幹部在網頁上改了 HuaXia 那邊的聲部名稱也照樣對得到
- 「曲目」步要每個沒擋下的群組都對到曲目（可以挑的現有曲目，或有曲名的新建曲目）才能按「下一步」
- 「聲部」步（`services/publish_service.py` 的 `plan_voices`，不改專案）把樂器表每一列對到群組的 HuaXia 曲目上的聲部（按下發譜時一起讀出，`PublishReadiness.parts`）：先用記住的手動配對（那個聲部在 HuaXia 已刪除就跳過）；再用「同一聲部」規則，被記住的配對佔走的不算，對到多個時不自動選、選單只列那幾個；都沒有就是沒對上。本專案有的聲部可以改選新建或名稱規則沒配給其他聲部的 HuaXia 聲部，挑了就記進專案。兩個泠靈聲部指到同一個 HuaXia 聲部、對到多個還沒挑、本專案沒有卻要建的聲部沒填最少人數時，寫出原因、「下一步」按不下去
- 要寫的內容：本專案有、沒對上的新建（泠靈的名稱，排在現有聲部之後）；本專案沒有、HuaXia 也沒有的預設不建，逐個勾「在 HuaXia 建」；對到的聲部名稱沿用 HuaXia 的，人數（HuaXia 的記法 `6`、`6-8`、`2↑`，`needed_min` 為最少人數）或聲部組不同時「覆寫」預設勾選（泠靈為定本），可以逐列取消。聲部組明確寫入；「其他」新建時寫成空白、交給 HuaXia 的觸發器 `guess_section`，對到現有聲部時不算差異也不寫。只有新建與覆寫，永遠不刪 HuaXia 的聲部；本專案沒有、HuaXia 已有的聲部不動。覆寫與建立的勾選只在這次預覽，不記在專案
- 新建的預設值是 `NewHuaXiaPiece.for_group(group)`：曲名＋樂章名稱，沒有樂章名稱用樂章編號，整首（兩者都沒有）只用曲名，曲名沒填時用群組名稱；作曲家帶入；時長由秒換算成分鐘（`duration_minutes`），四捨五入到 0.5 分鐘（`HUAXIA_DURATION_STEP_MINUTES`：HuaXia 編輯曲目的表單以 0.5 為一格，別的值會讓網頁表單擋下）；合奏

### 未存檔狀態

- 未存檔＝快照比對：`is_modified()` 比對目前內容（`to_data()`，即專案檔會存的內容，不含版本號）與上次存檔或開啟時的快照；改回原值就回到已存檔
- 開啟專案、切換分頁不改內容，不標記；切換介面語言改寫了命名格式就標記
- 每個編輯操作與存檔、開啟後都發出同一個「已變更」通知（`subscribe`，純 callback），主視窗以它更新標題的 `*`；存檔與預覽前沒有把畫面收回模型的步驟
- 關閉程式前，再用 `ProjectAccess.matches_file` 把目前內容和磁碟上的專案檔（照開啟方式還原、含遷移）比對一次；不同、讀不到或檔案已不在都詢問是否儲存。還沒存過檔的專案照快照判定（新專案沒動過就直接關閉）

### 舊格式遷移

- 遷移都在 `from_data` 內、拍快照之前完成，所以開啟舊專案不標記未存檔
- 群組的遷移只對舊版程式寫的專案檔做（`version` 在 `LEGACY_PROJECT_FILE_VERSIONS`，沒有這一欄也算）。內容：留空的總譜標籤補上依目前介面語言的預設值、專案層級的樂器表移進群組、勾選子集收成群組樂器表、舊分譜子資料夾旗標
- 專案層級的樂器表只在這裡遷移；命名與分割都只讀群組的樂器表
- **格式 3**（`INSTRUMENTATION_FILE_VERSION`）：比它舊的檔（含上一條的舊版）另遷移聲部組（`core/sections.py`）與人數
  - 樂團類型（檔裡沒有這一欄時）：已存的聲部組優先，沒存的聲部以國樂團的關鍵字偵測；出現吹管或彈撥就是國樂團，其餘為管弦樂團（`guess_orchestra_type`）
  - 聲部組（`migrate_sections`）：英文值先對回中文；國樂團中不在五組內的值（舊的弦樂、自訂文字等）依國樂團重新偵測，偵測不到的歸「其他」；管弦樂團的值不動。轉成以樂器為鍵時，同一樂器有多個值就依樂器表順序取第一個出現的值，鍵是那個聲部的寫法；留空的值丟掉
  - 人數（`_migrate_headcounts`）：每個群組的每個聲部，以同一聲部的規則（`voice_key`）查舊的專案層級人數（`instrument_headcounts`）；查到 n 就成為最少＝最多＝n（`Headcount(n)`），同一聲部在所有群組套用同一個值（舊對照裡同一聲部有幾種寫法時取第一個有值的）。0 與沒有值為未填，1 照轉；樂器表裡已沒有的殘留鍵丟掉，存檔不再寫這一欄
- 存檔寫 `PROJECT_FILE_VERSION`，其餘欄位不變；新版存的檔裡留空的總譜標籤與樂器表是使用者清掉的，再開啟不補回

### 較新的格式

- `version` 比 `PROJECT_FILE_VERSION` 新的專案檔由較新版本的泠靈建立：照樣開啟，但 `Project.read_only`，看不懂的欄位不讀進來
- 唯讀的專案不能存檔，也不提供另存（另存同樣會丟掉看不懂的欄位）：`ProjectService.save_project` 丟出 `ReadOnlyProjectError`、什麼都不寫；主視窗開啟時寫明「這個專案檔由較新版本的泠靈建立」，停用「儲存專案」與「另存新檔」，標題標「唯讀」，開新專案、開啟其他專案與關閉時不詢問是否儲存
- 存不了檔，所以唯讀時主視窗也停用所有會改專案，或搬動、產生它引用的檔案的操作：預覽並重新命名、分割、復原與重做、匯入、新增群組與連成樂章、樂團類型、命名格式、編制表（`InstrumentationTable.set_editable`）與各分頁的內容（分頁仍可切換），關閉時才不會有存不了的修改。旋轉與壓縮不改專案，照常可用。停用與否只在 `MainWindow._show_enabled_state` 判斷（連同背景工作進行中的停用）
- 已發佈的舊版泠靈沒有這道檢查，所以 README 寫明升級後不要再用舊版開專案

### 自動偵測

- 偵測只在檔案進入群組時做：匯入資料夾建立群組、從勾選建立群組、把檔案搬進群組、加入檔案、分割結果加入群組。沒有總譜才依 `SCORE_KEYWORDS` 猜總譜，沒有曲名才由分譜檔名猜曲名，已有的不覆蓋
- 建立分頁與開啟專案時不偵測：使用者清掉的總譜或曲名，要等下一次有檔案進入該群組才會照上一條重猜
- 「自動偵測」按鈕（`guess_piece_name`）重猜曲名，取代目前的值

## 專案存取

開啟與存檔一律經過專案存取（`services/project_access.py` 的 `ProjectAccess`），主視窗只呼叫它並依結果顯示訊息。它擁有專案檔讀寫、最近專案清單、工作區 meta 的所屬專案與已知專案清單。

- **專案檔本身讀寫成功就算成功**：`open`／`save` 回傳 `AccessResult`，`error` 只反映專案檔本身。附帶動作寫不進去（最近清單 `recent_failed`、meta 的所屬專案 `owner_failed`）只在狀態列提示，不跳錯誤框，也不擋下關閉、開新專案或開啟其他專案（推翻 #16 原本「最近清單寫不進去也算存檔失敗」的決定）。兩個附帶動作各自進行，一個失敗不影響另一個
- 存檔：專案檔寫成後，專案的快照就是寫出的內容（`ProjectService.save_project` 寫完才 `mark_saved`）；寫不成時顯示「儲存失敗」、不做任何附帶動作，專案仍判為未存檔
- 開啟：讀不到或格式不對時顯示「無法開啟專案」，不換掉目前的專案；專案檔已不存在時另外從最近清單移除（讀不到的留在清單上）。從最近清單開啟時先以 `forget_if_missing` 檢查，不存在就提示「找不到檔案」並移除，不先問是否儲存。開啟結果帶出專案引用、但找不到的檔案（`missing_files`，只在譜庫的不算，另列在 `catalog_only_files`），主視窗據此提醒
- 開啟與存檔時更新引用到的工作區子資料夾的 `meta.project_path`；`update_project_path` 回傳寫入失敗的子資料夾，就是上面的 `owner_failed`
- 最近清單：開啟或存檔的專案放到頂端，同一個檔案（任何寫法）只留一筆，最多 `MAX_RECENT_PROJECTS` 筆；規則由 `ProjectAccess` 維護，存在偏好設定裡（`PreferencesService` 只負責存放）
- **已知專案**（`known_projects`）＝最近清單＋各工作區子資料夾 `meta.project_path` 指向的專案檔，是「清理工作區」判定引用關係時載入的候選（`scan_workspace`，見 [workspace.md](workspace.md)）；掃描順手把最近清單中已不存在的專案檔移除

## 匯入

- 匯入檔案（可多選）：只收存在的 `.pdf`，全部進未分組
- 匯入資料夾（一次一個，`ImportService.import_folder`）：有含 PDF 的子資料夾時，每個這樣的子資料夾建一個以它命名的群組，根目錄的 PDF 進未分組；沒有時整個資料夾建一個以它命名的群組。只掃一層子資料夾、只收 `.pdf`；總譜、曲名與總譜標籤在群組加進專案時處理（見上方自動偵測）
